<h2>二、OpenClaw Gateway 架构 | OpenClaw Gateway Architecture</h2>
<p><strong>中文</strong></p>
<h3>2.1 整体架构</h3>
<div class="note"><p><strong>架构图（Mermaid 源码）</strong> / <em>Architecture diagram (Mermaid source)</em></p><pre><code>flowchart TB
    subgraph Clients["客户端"]
        PHONE[手机聊天 App]
        WEB[Web Control UI]
        MAC[macOS App]
        IOS[iOS/Android Nodes]
    end

    subgraph GW["OpenClaw Gateway :18789"]
        WS[WebSocket Server]
        ROUTE[会话路由 sessionKey]
        AUTH[认证 gateway.auth]
        TOOLS[工具执行]
        MEM[记忆读写]
    end

    subgraph Agent["Agent Runtime"]
        WP[Workspace 文件注入]
        SK[Skills 加载]
        LLM[LLM 调用]
    end

    PHONE --&gt; WS
    WEB --&gt; WS
    MAC --&gt; WS
    IOS --&gt; WS
    WS --&gt; ROUTE
    ROUTE --&gt; Agent
    Agent --&gt; TOOLS
    Agent --&gt; MEM
    Agent --&gt; WS</code></pre></div>
<p>OpenClaw 没有独立的「编排微服务层」——Gateway 接收消息、路由会话、调用 LLM、执行工具、写回响应，全部在一个进程中完成。</p>
<h3>2.2 消息处理流程</h3>
<pre><code class="language-text">1. 聊天 App 发来消息
2. Gateway 接收（WebSocket / 渠道 Webhook）
3. 解析 sessionKey（路由键，非授权令牌）
4. 加载对应 Agent 的 Workspace 文件 + Skills
5. 组装系统提示词，调用 LLM
6. 若有工具调用 → 执行 shell/文件/浏览器/API
7. 响应经 Gateway 发回原渠道
</code></pre>
<h3>2.3 会话路由（sessionKey）</h3>
<p><code>sessionKey</code> 是<strong>路由选择器</strong>，决定使用哪个会话上下文，<strong>不是</strong>用户认证令牌。</p>
<p>常见隔离策略（<code>session.dmScope</code>）：</p>
<table>
<thead>
<tr>
<th>值</th>
<th>行为</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>per-channel-peer</code></td>
<td>每个发送者独立会话（推荐多用户 DM）</td>
</tr>
<tr>
<td><code>per-account-channel-peer</code></td>
<td>多账号渠道下按账号+发送者隔离</td>
</tr>
</tbody>
</table>
<h3>2.4 多 Agent 路由</h3>
<p>OpenClaw 支持在同一 Gateway 上运行多个 Agent，按工作区、发送者或规则路由：</p>
<pre><code class="language-text">Gateway
├── Agent A（工作区 ~/.openclaw/workspace-personal）
├── Agent B（工作区 ~/.openclaw/workspace-work）
└── 路由规则 → 按 channel / sender / mention 分发
</code></pre>
<h3>2.5 渠道接入</h3>
<p><strong>内置渠道</strong>：WhatsApp、Telegram、Discord、Slack、Signal、iMessage、Google Chat、Microsoft Teams、WebChat 等。</p>
<p><strong>插件渠道</strong>：Matrix、Nostr、Twitch、Zalo、Feishu 等通过 bundled 或 external channel plugins 扩展。</p>
<p><strong>Nodes（移动端）</strong>：iOS/Android 设备配对后提供 Canvas、相机、语音等工作流。</p>
<h3>2.6 配置中心</h3>
<p>主配置文件：<code>~/.openclaw/openclaw.json</code></p>
<pre><code class="language-json5">{
  gateway: {
    mode: "local",
    bind: "loopback",
    auth: { mode: "token", token: "long-random-token" },
  },
  channels: {
    whatsapp: {
      dmPolicy: "pairing",
      groups: { "*": { requireMention: true } },
    },
  },
  tools: {
    profile: "messaging",
    exec: { security: "deny", ask: "always" },
  },
}
</code></pre>
<h3>2.7 Web Control UI</h3>
<p>本地默认：<code>http://127.0.0.1:18789/</code></p>
<p>提供聊天、配置、会话管理、节点配对的浏览器控制台。远程访问需 Tailscale 或 SSH 隧道。</p>
<p><strong>English</strong></p>
<h3>2.1 Overall Architecture</h3>
<p>Single TypeScript process on port 18789: WebSocket server handles all channels, session routing, tool execution, and memory I/O. No separate orchestration microservice — the Gateway <em>is</em> the product.</p>
<h3>2.2 Message Flow</h3>
<p>Chat app → Gateway (WebSocket/webhook) → sessionKey routing → load workspace + skills → LLM → tools → response back to channel.</p>
<h3>2.3 Session Routing (sessionKey)</h3>
<p><code>sessionKey</code> is a <strong>routing selector</strong>, not an auth token. <code>session.dmScope</code> controls DM isolation (e.g., <code>per-channel-peer</code> for multi-user inboxes).</p>
<h3>2.4 Multi-Agent Routing</h3>
<p>Multiple agents on one Gateway, routed by workspace, sender, or rules.</p>
<h3>2.5 Channel Integration</h3>
<p>Built-in channels (WhatsApp, Telegram, Discord, etc.) plus plugin channels (Matrix, Zalo, etc.) and iOS/Android nodes.</p>
<h3>2.6 Configuration</h3>
<p>Central config at <code>~/.openclaw/openclaw.json</code> — gateway mode, auth, channel policies, tool profiles.</p>
<h3>2.7 Web Control UI</h3>
<p>Browser dashboard at <code>http://127.0.0.1:18789/</code> for chat, config, sessions, and node pairing.</p>

<h3>3.3 消息处理流程</h3>
<pre><code class="language-text">平台事件 → Adapter.on_message() → MessageEvent
        → GatewayRunner._handle_message()
            1. 解析 session key
            2. 用户授权检查
            3. 斜杠命令？→ 命令处理器
            4. Agent 正在运行？→ 双层守卫（排队/中断/审批）
            5. 创建 AIAgent → run_conversation()
            6. 响应经 Adapter 发回
</code></pre>
<h3>3.4 Session Key 格式</h3>
<pre><code class="language-text">agent:main:{platform}:{chat_type}:{chat_id}
</code></pre>
<p>示例：<code>agent:main:telegram:private:123456789</code></p>
<p>线程型平台（Telegram 论坛话题、Discord/Slack 线程）在 <code>chat_id</code> 中包含线程 ID。<strong>禁止手动拼接</strong>，应使用 <code>build_session_key()</code>。</p>
<h3>3.5 双层消息守卫</h3>
<p>Agent 正在处理消息时，新消息经过两级拦截：</p>
<p><strong>Level 1 — Base Adapter</strong>（<code>gateway/platforms/base.py</code>）：<br/>
- 检查 <code>_active_sessions</code><br/>
- 活跃会话 → 消息入 <code>_pending_messages</code> 队列，设置中断事件</p>
<p><strong>Level 2 — GatewayRunner</strong>（<code>gateway/run.py</code>）：<br/>
- 检查 <code>_running_agents</code><br/>
- <code>/stop</code>、<code>/approve</code>、<code>/deny</code> 等命令绕过守卫，内联分发<br/>
- 其他消息触发 <code>running_agent.interrupt()</code></p>
<h3>3.6 用户授权</h3>
<p>授权检查顺序（<code>_is_user_authorized()</code>）：</p>
<ol>
<li>平台级 allow-all（如 <code>DISCORD_ALLOW_ALL_USERS=true</code>）</li>
<li>DM 配对已批准列表</li>
<li>平台 allowlist（如 <code>TELEGRAM_ALLOWED_USERS=12345,67890</code>）</li>
<li>全局 allowlist（<code>GATEWAY_ALLOWED_USERS</code>）</li>
<li>全局 allow-all（<code>GATEWAY_ALLOW_ALL_USERS=true</code>）</li>
<li><strong>默认：拒绝</strong></li>
</ol>
<p>未配置任何 allowlist 时，启动日志会警告所有未授权用户将被拒绝。</p>
<h3>3.7 DM 配对流程</h3>
<pre><code class="language-text">未知用户发 DM → Bot 回复 8 位配对码
管理员 CLI：hermes pairing approve telegram ABC12DEF
用户永久授权（存储于 ~/.hermes/pairing/）
</code></pre>
<p>安全特性：密码学随机、1 小时 TTL、10 分钟速率限制、5 次失败锁定 1 小时。</p>

<p><strong>English</strong></p>
<h3>3.1 Overall Architecture</h3>
<p><code>GatewayRunner</code> is the messaging frontend for the shared <code>AIAgent</code> engine. 20+ platform adapters normalize inbound events; the runner handles auth, slash commands, agent creation, and delivery.</p>
<h3>3.2 Key Source Files</h3>
<p><code>gateway/run.py</code> (runner), <code>session.py</code> (persistence), <code>delivery.py</code> (outbound), <code>pairing.py</code> (DM auth), <code>platforms/*.py</code> (adapters).</p>
<h3>3.3 Message Flow</h3>
<p>Platform event → adapter → <code>_handle_message()</code> → auth → slash command or AIAgent → response via adapter.</p>
<h3>3.4 Session Key</h3>
<p><code>agent:main:{platform}:{chat_type}:{chat_id}</code> — use <code>build_session_key()</code>, never construct manually.</p>
<h3>3.5 Two-Level Message Guard</h3>
<p>Adapter-level queuing + runner-level interrupt/approval routing while agent is active.</p>
<h3>3.6 User Authorization</h3>
<p>Layered allowlists + DM pairing; default deny if no allowlist configured.</p>
<h3>3.7 DM Pairing</h3>
<p>8-char cryptographic codes, TTL, rate limits, lockout. Approved via <code>hermes pairing approve</code>.</p>
<h3>3.8 Shared Slash Commands</h3>
<p>CLI and Gateway share <code>COMMAND_REGISTRY</code> — <code>/model</code>, <code>/skills</code>, <code>/stop</code>, <code>/approve</code>, etc.</p>
<h3>3.9 Delivery Modes</h3>
<p>Direct reply, home channel, explicit target, cross-platform. Cron deliveries excluded from gateway session history.</p>
<h3>3.10 Platform Adapters</h3>

<h2>五、部署模式 | Deployment Patterns</h2>
<p><strong>中文</strong></p>
<h3>模式 A：本地 Loopback（最安全）</h3>
<pre><code class="language-text">笔记本 localhost → Gateway → 仅本机 Control UI / 本地渠道
</code></pre>
<ul>
<li>OpenClaw：<code>gateway.bind: "loopback"</code></li>
<li>Hermes：Gateway 默认不暴露 HTTP 端口</li>
</ul>
<h3>模式 B：VPS + 消息平台（最常见）</h3>
<pre><code class="language-text">$5 VPS → Gateway 长驻 → Telegram/WhatsApp Bot Token
用户在手机上对话，Agent 在云端执行
</code></pre>
<ul>
<li>Hermes 推荐 <code>terminal.backend: docker</code> 隔离命令执行</li>
<li>OpenClaw 推荐 <code>openclaw security audit</code> 加固</li>
</ul>
<h3>模式 C：分离式（高安全）</h3>
<pre><code class="language-text">Gateway 机器（仅消息）──SSH──→ 执行机器（Docker 沙箱）
</code></pre>
<ul>
<li>Hermes 原生支持：<code>terminal.backend: ssh</code></li>
<li>OpenClaw：通过 sandbox 配置 + 远程 node</li>
</ul>
<h3>模式 D：Serverless（Hermes 独有）</h3>
<pre><code class="language-text">Gateway 在 VPS → Agent 命令发往 Modal/Daytona
空闲休眠，按需唤醒，接近零闲置成本
</code></pre>
<p><strong>English</strong></p>
<p><strong>Pattern A — Local loopback</strong> (safest): bind to localhost only.</p>
<p><strong>Pattern B — VPS + messaging</strong> (most common): long-running Gateway on cheap VPS, chat from phone.</p>
<p><strong>Pattern C — Split trust</strong> (high security): Gateway on one host, execution on another via SSH/Docker sandbox.</p>
<p><strong>Pattern D — Serverless</strong> (Hermes-specific): Modal/Daytona backends with sleep-on-idle.</p>

<h2>七、结语 | Conclusion</h2>
<p><strong>中文</strong></p>
<p>OpenClaw Gateway 是 <strong>「多渠道操作系统」</strong> — 用单一 WebSocket 控制平面统一 50+ 渠道，适合需要极致连接广度与浏览器控制台的场景。Hermes Gateway 是 <strong>「Agent 引擎的消息前端」</strong> — 20 个 Adapter 接入同一 AIAgent 核心，与 CLI、ACP、Cron 共享会话存储与斜杠命令，适合需要统一学习闭环与跨入口一致体验的场景。二者都能让你「在 Telegram 上发消息、Agent 在云端干活」，选型应优先考虑你对 <strong>连接广度</strong> 还是 <strong>引擎深度</strong> 的需求。</p>
<p><strong>English</strong></p>
<p>OpenClaw Gateway is a <strong>multi-channel operating system</strong> — one WebSocket control plane for 50+ channels, ideal for maximum connectivity and a browser dashboard. Hermes Gateway is the <strong>messaging frontend for the agent engine</strong> — 20 adapters into one AIAgent core, sharing session storage and slash commands with CLI, ACP, and Cron. Both let you "message from Telegram while the agent works in the cloud"; choose based on whether you need <strong>connectivity breadth</strong> or <strong>engine depth</strong>.</p>
