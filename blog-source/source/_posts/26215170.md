<h2>一、共同前提：个人助理信任模型 | Shared Premise: Personal Assistant Trust Model</h2>
<p><strong>中文</strong></p>
<p>两个框架都面向 <strong>单用户/单信任边界</strong> 的个人助理场景，而非 hostile multi-tenant（敌对多租户）隔离：</p>
<table>
<thead>
<tr>
<th>假设</th>
<th>含义</th>
</tr>
</thead>
<tbody>
<tr>
<td>单操作者</td>
<td>一个 Gateway 对应一个信任的操作者</td>
</tr>
<tr>
<td>主机可信</td>
<td>能修改 <code>~/.openclaw</code> 或 <code>~/.hermes</code> 的人视为可信管理员</td>
</tr>
<tr>
<td>非多租户边界</td>
<td>多个互不信任用户共享同一 Gateway <strong>不是</strong>推荐部署模式</td>
</tr>
<tr>
<td>工具即权限</td>
<td>能触发 Agent 的人 ≈ 能诱导 Agent 使用其工具权限</td>
</tr>
</tbody>
</table>
<p>若需敌对用户隔离，应 <strong>拆分信任边界</strong>：独立 Gateway + 独立凭证 + 理想情况下独立 OS 用户/主机。</p>
<p><strong>English</strong></p>
<p>Both frameworks target <strong>single-user / single-trust-boundary</strong> personal assistant deployments, not hostile multi-tenant isolation:</p>
<table>
<thead>
<tr>
<th>Assumption</th>
<th>Meaning</th>
</tr>
</thead>
<tbody>
<tr>
<td>Single operator</td>
<td>One Gateway per trusted operator</td>
</tr>
<tr>
<td>Host is trusted</td>
<td>Anyone who can modify <code>~/.openclaw</code> or <code>~/.hermes</code> is a trusted admin</td>
</tr>
<tr>
<td>Not multi-tenant</td>
<td>Multiple mutually untrusted users on one Gateway is <strong>not</strong> a recommended setup</td>
</tr>
<tr>
<td>Tools = authority</td>
<td>Anyone who can trigger the agent can induce tool usage within the agent's policy</td>
</tr>
</tbody>
</table>
<p>For adversarial-user isolation, <strong>split trust boundaries</strong>: separate Gateways, credentials, and ideally OS users/hosts.</p>

<h2>三、OpenClaw 安全模型 | OpenClaw Security Model</h2>
<p><strong>中文</strong></p>
<h3>3.1 威胁模型</h3>
<p>Agent 可以：执行任意 Shell、读写文件、访问网络、代发消息。</p>
<p>消息者可以：Prompt 注入、社会工程、探测基础设施。</p>
<p>OpenClaw 的应对：<strong>先决定谁能说话，再决定 Agent 能在哪行动，最后假设模型可被操纵并限制爆炸半径。</strong></p>
<h3>3.2 信任边界矩阵</h3>
<table>
<thead>
<tr>
<th>控制项</th>
<th>实际作用</th>
<th>常见误读</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>gateway.auth</code></td>
<td>认证 Gateway API 调用者</td>
<td>「每帧都需签名才安全」</td>
</tr>
<tr>
<td><code>sessionKey</code></td>
<td>会话路由键</td>
<td>「sessionKey 是用户认证」</td>
</tr>
<tr>
<td>Prompt 防护</td>
<td>降低模型滥用风险</td>
<td>「注入 alone 即证明认证绕过」</td>
</tr>
<tr>
<td>Node pairing</td>
<td>操作者级远程执行</td>
<td>「应默认视为不可信用户访问」</td>
</tr>
<tr>
<td>Exec approvals</td>
<td>操作者意图护栏</td>
<td>「非敌对多租户隔离」</td>
</tr>
</tbody>
</table>
<h3>3.3 DM 访问模型</h3>
<p>所有支持 DM 的渠道均有 <code>dmPolicy</code>：</p>
<table>
<thead>
<tr>
<th>策略</th>
<th>行为</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>pairing</code>（默认）</td>
<td>未知发送者收到配对码，需管理员批准</td>
</tr>
<tr>
<td><code>allowlist</code></td>
<td>仅白名单内 ID 可对话</td>
</tr>
<tr>
<td><code>open</code></td>
<td>任何人可触发（高风险）</td>
</tr>
<tr>
<td><code>disabled</code></td>
<td>禁用 DM</td>
</tr>
</tbody>
</table>
<p>群组策略：<code>requireMention: true</code> 防止群内误触发。</p>
<h3>3.4 上下文可见性（contextVisibility）</h3>
<p>控制<strong>注入模型的补充上下文</strong>（引用回复、线程历史），与触发授权分离：</p>
<table>
<thead>
<tr>
<th>值</th>
<th>行为</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>all</code>（默认）</td>
<td>保留所有补充上下文</td>
</tr>
<tr>
<td><code>allowlist</code></td>
<td>仅白名单发送者的上下文</td>
</tr>
<tr>
<td><code>allowlist_quote</code></td>
<td>白名单过滤，但保留一条显式引用</td>
</tr>
</tbody>
</table>
<h3>3.5 工具爆炸半径控制</h3>
<p><strong>硬化基线配置</strong>（60 秒快速加固）：</p>
<pre><code class="language-json5">{
  gateway: {
    mode: "local",
    bind: "loopback",
    auth: { mode: "token", token: "replace-with-long-random-token" },
  },
  session: { dmScope: "per-channel-peer" },
  tools: {
    profile: "messaging",
    deny: ["group:automation", "group:runtime", "group:fs",
           "sessions_spawn", "sessions_send"],
    fs: { workspaceOnly: true },
    exec: { security: "deny", ask: "always" },
    elevated: { enabled: false },
  },
  channels: {
    whatsapp: {
      dmPolicy: "pairing",
      groups: { "*": { requireMention: true } },
    },
  },
}
</code></pre>
<p><strong>高风险控制面工具</strong>（对不可信内容默认 deny）：</p>
<ul>
<li><code>gateway</code> — 可修改持久配置</li>
<li><code>cron</code> — 可创建持久定时任务</li>
<li><code>sessions_spawn</code> / <code>sessions_send</code> — 跨会话操作</li>
</ul>

<thead>
<tr>
<th>配置</th>
<th>含义</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>tools.exec.security</code></td>
<td><code>deny</code> / <code>allowlist</code> / <code>full</code></td>
</tr>
<tr>
<td><code>tools.exec.ask</code></td>
<td><code>always</code> / <code>on-miss</code> / <code>off</code></td>
</tr>
<tr>

<p>默认对个人助理：<code>security="full"</code>, <code>ask="off"</code> — 这是<strong>有意为之的 UX 默认</strong>，非漏洞。</p>
<p>审批绑定精确请求上下文；无法识别单一本地文件操作数的解释器命令会被拒绝。</p>

<ul>
<li>根目录边界文件访问</li>
<li>原子写入</li>
<li>安全归档解压</li>
<li>密钥文件辅助函数</li>
</ul>
<h3>3.8 网络安全</h3>
<table>
<thead>
<tr>
<th>风险</th>
<th>缓解</th>
</tr>
</thead>
<tbody>
<tr>
<td>Gateway 公网暴露</td>
<td><code>bind: "loopback"</code> + Tailscale</td>
</tr>
<tr>
<td>反向代理认证绕过</td>
<td>配置 <code>gateway.trustedProxies</code>，拒绝未信任代理的 localhost 伪装</td>

<h3>3.9 插件与 Skills 供应链</h3>
<ul>
<li>插件在 Gateway <strong>进程内</strong>运行 — 视为可信代码</li>
<li>推荐 <code>plugins.allow</code> 显式白名单</li>
<li>Skills 目录视为可信代码，限制修改权限</li>
<li><code>openclaw security audit --deep</code> 扫描 Skills/插件</li>
<li>发布包使用 <code>npm-shrinkwrap.json</code> 锁定依赖图</li>
</ul>
<h3>3.10 安全审计</h3>
<pre><code class="language-bash">openclaw security audit          # 常规审计
openclaw security audit --deep   # 含实时 Gateway 探测
openclaw security audit --fix    # 自动修复常见问题
</code></pre>
<p>审计覆盖：入站访问、工具爆炸半径、网络暴露、浏览器控制、文件权限、插件、策略漂移。</p>
<p><strong>English</strong></p>
<h3>3.1 Threat Model</h3>
<p>The agent can execute shell, read/write files, access network, send messages. Messengers can prompt-inject and social-engineer. Response: control who can talk, where the agent acts, assume the model is manipulable, limit blast radius.</p>
<h3>3.2 Trust Boundary Matrix</h3>
<p><code>gateway.auth</code> authenticates API callers; <code>sessionKey</code> routes sessions (not auth); exec approvals are operator guardrails, not multi-tenant isolation.</p>
<h3>3.3 DM Access Model</h3>
<p><code>dmPolicy</code>: pairing (default), allowlist, open (high risk), disabled. Group mention gates prevent accidental triggers.</p>
<h3>3.4 Context Visibility</h3>
<p>Separates trigger authorization from supplemental context injection (<code>all</code>, <code>allowlist</code>, <code>allowlist_quote</code>).</p>
<h3>3.5 Tool Blast Radius</h3>
<p>Hardened baseline denies automation/runtime/fs tools, enables workspace-only filesystem, denies exec by default. Deny <code>gateway</code>, <code>cron</code>, <code>sessions_spawn</code> for untrusted surfaces.</p>
<h3>3.6 Exec Approvals</h3>
<p><code>security</code> + <code>ask</code> + <code>host</code> configuration. Default <code>full</code>/<code>off</code> is intentional for trusted personal assistants.</p>
<h3>3.7 Secure File Operations</h3>
<p><code>@openclaw/fs-safe</code>: root-bounded access, atomic writes, safe archive extraction.</p>
<h3>3.8 Network Security</h3>
<p>Loopback bind, trusted proxy config, HTTPS for Control UI, no direct public exposure.</p>
<h3>3.9 Plugin &amp; Skills Supply Chain</h3>
<p>In-process plugins = trusted code. Explicit allowlists, shrinkwrapped npm deps, deep audit scanning.</p>
<h3>3.10 Security Audit</h3>
<p><code>openclaw security audit [--deep] [--fix]</code> covers inbound access, tool blast radius, network exposure, permissions, plugins, policy drift.</p>

<h2>四、Hermes Agent 安全模型 | Hermes Agent Security Model</h2>
<p><strong>中文</strong></p>
<h3>4.1 七层纵深防御</h3>
<div class="note"><p><strong>架构图（Mermaid 源码）</strong> / <em>Architecture diagram (Mermaid source)</em></p><pre><code>flowchart TB
    L1[1. 用户授权&lt;br/&gt;Allowlist + DM Pairing]
    L2[2. 危险命令审批&lt;br/&gt;Pattern + Tirith]
    L3[3. 容器隔离&lt;br/&gt;Docker/Modal/Daytona]
    L4[4. MCP 凭证过滤&lt;br/&gt;环境变量隔离]
    L5[5. 上下文文件扫描&lt;br/&gt;Prompt 注入检测]
    L6[6. 跨会话隔离&lt;br/&gt;Cron 路径加固]
    L7[7. 输入净化&lt;br/&gt;工作目录 Allowlist]

    L1 --&gt; L2 --&gt; L3 --&gt; L4 --&gt; L5 --&gt; L6 --&gt; L7</code></pre></div>
<h3>4.2 危险命令审批</h3>
<p><strong>审批模式</strong>（<code>~/.hermes/config.yaml</code>）：</p>
<table>
<thead>
<tr>
<th>模式</th>
<th>行为</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>manual</code>（默认）</td>
<td>所有危险命令需用户明确批准</td>
</tr>
<tr>
<td><code>smart</code></td>
<td>辅助 LLM 评估风险；低风险自动批准，高风险自动拒绝，不确定则人工</td>
</tr>
<tr>
<td><code>off</code></td>
<td>禁用所有审批（等同 <code>--yolo</code>）</td>
</tr>
</tbody>
</table>
<p><strong>YOLO 模式</strong>（<code>/yolo</code> 或 <code>hermes --yolo</code>）：<br/>
- 绕过审批提示，但<strong>不绕过硬线黑名单</strong><br/>
- 会话中显示红色 <code>⚠ YOLO</code> 状态栏提醒</p>
<p><strong>硬线黑名单（Always-On Floor）</strong> — 无论 YOLO/off/approve 均拒绝：</p>
<table>
<thead>
<tr>
<th>模式</th>
<th>原因</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>rm -rf /</code> 及变体</td>
<td>擦除文件系统根</td>
</tr>
<tr>
<td>Bash fork bomb</td>
<td>耗尽进程直到重启</td>
</tr>
<tr>
<td><code>mkfs.*</code> on root device</td>
<td>格式化 live 系统</td>
</tr>
<tr>
<td><code>dd if=/dev/zero of=/dev/sd*</code></td>
<td>清零物理磁盘</td>
</tr>
<tr>
<td>管道不可信 URL 到 sh</td>
<td>远程代码执行</td>
</tr>
</tbody>
</table>
<p><strong>触发审批的模式</strong>（部分）：</p>
<ul>
<li><code>rm -r</code> / <code>rm --recursive</code></li>
<li><code>chmod 777</code> / <code>chmod -R</code> 不安全权限</li>
<li><code>DROP TABLE</code> / <code>DELETE FROM</code> 无 WHERE / <code>TRUNCATE</code></li>
<li><code>systemctl stop/restart/disable</code></li>
<li><code>bash -c</code> / <code>curl | sh</code> / <code>bash &lt;(curl ...)</code></li>
<li>覆写 <code>/etc/</code>、<code>~/.ssh/</code>、<code>~/.hermes/.env</code></li>
<li><code>pkill</code>/<code>killall</code> hermes/gateway（防自终止）</li>
</ul>
<p><strong>容器绕过</strong>：Docker/Singularity/Modal/Daytona 后端跳过危险命令检查——容器本身是安全边界。</p>
<h3>4.3 Tirith 预执行扫描</h3>
<p>集成 tirith 进行内容级命令扫描，检测：</p>
<ul>
<li>同形字 URL 欺骗</li>
<li>管道到解释器（<code>curl | bash</code>）</li>
<li>终端注入攻击</li>
</ul>
<pre><code class="language-yaml">security:
  tirith_enabled: true
  tirith_timeout: 5
  tirith_fail_open: true   # tirith 不可用时是否放行（高安全环境设为 false）
</code></pre>
<p>可疑/阻断命令触发审批流程，默认选择 deny。</p>

<p>授权检查顺序：</p>

<li>DM 配对已批准列表</li>
<li>平台 allowlist</li>
<li>全局 allowlist</li>
<li>全局 allow-all</li>
<li><strong>默认拒绝</strong></li>
</ol>
<p><strong>DM 配对安全特性</strong>（OWASP + NIST SP 800-63-4）：</p>

<h3>4.5 容器隔离（Docker 示例）</h3>
<p>每个容器强制安全参数：</p>
<pre><code class="language-python">"--cap-drop", "ALL"
"--security-opt", "no-new-privileges"
"--pids-limit", "256"
"--tmpfs", "/tmp:rw,nosuid,size=512m"
"--tmpfs", "/var/tmp:rw,noexec,nosuid,size=256m"
</code></pre>
<p>可配置 CPU/内存/磁盘限制。持久模式 bind-mount <code>/workspace</code> 和 <code>/root</code>；临时模式使用 tmpfs。</p>

<h3>4.1 Seven Defense Layers</h3>
<p>User auth → dangerous command approval → container isolation → MCP credential filtering → context file scanning → cross-session isolation → input sanitization.</p>
<h3>4.2 Dangerous Command Approval</h3>
<p>Modes: <code>manual</code> (default), <code>smart</code> (auxiliary LLM risk assessment), <code>off</code> (YOLO). Hardline blocklist always blocks catastrophic commands regardless of YOLO. Container backends skip approval checks — the container is the boundary.</p>
<h3>4.3 Tirith Pre-Exec Scanning</h3>
<p>Content-level scanning for homograph spoofing, pipe-to-interpreter, terminal injection. Integrates with approval flow; default deny on suspicious verdicts.</p>
<h3>4.4 User Authorization</h3>
<p>Layered allowlists + DM pairing (cryptographic codes, TTL, rate limits, lockout). Default deny.</p>
<h3>4.5 Container Isolation</h3>
<p>Docker: cap-drop ALL, no-new-privileges, pids-limit, size-limited tmpfs. Configurable CPU/memory/disk.</p>
<h3>4.6 Terminal Backend Security</h3>
<p>local/ssh: approval checks on. docker/singularity/modal/daytona: container is boundary, checks skipped.</p>
<h3>4.7 Credential Filtering</h3>
<p>Strip sensitive env vars by default. Skill-declared passthrough only when skill is loaded. MCP gets filtered env + explicit config only. Error message redaction.</p>
<h3>4.8 SSRF &amp; Website Policy</h3>
<p>Block private/loopback/link-local/metadata addresses. Redirect re-validation. Optional <code>allow_private_urls</code> for LAN-only setups. Domain blocklist support.</p>
<h3>4.9 Context File Injection Protection</h3>
<p>Scan workspace files for injection patterns, hidden comments, secret exfiltration, invisible Unicode.</p>
<h3>4.10 Memory Security Scanning</h3>
<p>Scan memory entries before system-prompt injection.</p>
<h3>4.11 Skills Supply Chain</h3>
<p>Hub install security scan, trust levels, <code>--force</code> cannot override <code>dangerous</code> verdicts, lazy dep isolation.</p>
<h3>4.12 Supply-Chain Advisories</h3>
<p><code>hermes doctor</code> flags known compromised package versions.</p>

<h2>六、共享收件箱场景 | Shared Inbox Scenarios</h2>
<p><strong>中文</strong></p>
<p>若多人可 DM 你的 Bot，核心风险是 <strong>委派工具权限</strong>：</p>
<ul>
<li>任一允许发送者可诱导 <code>exec</code>、浏览器、网络/文件工具</li>
<li>一个发送者的 Prompt 注入可影响共享状态/设备/输出</li>
<li>若 Agent 持有敏感凭证，任何允许发送者都可能驱动外泄</li>
</ul>
<p><strong>OpenClaw 建议</strong>：<br/>
- <code>session.dmScope: "per-channel-peer"</code><br/>
- <code>dmPolicy: "pairing"</code> 或严格 allowlist<br/>
- 不要对共享 DM 开放广泛工具访问<br/>
- 团队工作流用独立 Agent/Gateway，最小工具集</p>
<p><strong>Hermes 建议</strong>：<br/>
- 配置平台 allowlist，禁用 <code>GATEWAY_ALLOW_ALL_USERS</code><br/>
- 生产环境 <code>terminal.backend: docker</code><br/>
- Cron 任务设 <code>cron_mode: deny</code>（遇危险命令拒绝而非自动批准）</p>
<p><strong>English</strong></p>
<p>If multiple people can DM your bot, the core risk is <strong>delegated tool authority</strong>. Any allowed sender can induce exec/browser/network tools; prompt injection from one sender affects shared state.</p>
<p><strong>OpenClaw</strong>: per-channel-peer DM scope, pairing/allowlist, no broad tools on shared DMs, separate agents for team workflows.</p>
<p><strong>Hermes</strong>: platform allowlists, Docker backend in production, <code>cron_mode: deny</code> for headless jobs.</p>

<h2>八、结语 | Conclusion</h2>
<p><strong>中文</strong></p>
<p>OpenClaw 的安全模型是 <strong>「身份先行、范围次之、模型最后」</strong> — 用 Gateway 认证、DM 策略、工具 Profile 和 Exec 审批控制爆炸半径，默认信任单操作者，适合快速搭建个人助理并通过 <code>security audit</code> 渐进加固。Hermes 的安全模型是 <strong>「七层纵深、默认审慎」</strong> — 危险命令人工审批、硬线黑名单、Tirith 扫描、容器隔离、凭证过滤环环相扣，适合对命令执行安全有更高要求的长期运行场景。两者都不是敌对多租户沙箱；若需此类隔离，唯一可靠方案是 <strong>拆分信任边界</strong>，而非在单一 Gateway 上叠加更多审批规则。</p>
<p><strong>English</strong></p>
<p>OpenClaw's security model is <strong>identity first, scope second, model last</strong> — Gateway auth, DM policies, tool profiles, and exec approvals control blast radius, defaulting to trusted single-operator UX, hardened progressively via <code>security audit</code>. Hermes's model is <strong>seven-layer defense-in-depth with cautious defaults</strong> — manual approval, hardline blocklist, Tirith scanning, container isolation, and credential filtering for higher-assurance long-running deployments. Neither is a hostile multi-tenant sandbox; for that, the only reliable approach is <strong>splitting trust boundaries</strong>, not piling more approval rules onto one Gateway.</p>
